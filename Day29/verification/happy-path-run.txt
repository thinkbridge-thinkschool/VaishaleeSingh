WHAT THIS RUN PROVES, AND WHAT IT DOES NOT

Proves, because nothing here is stubbed: four module schemas migrate and
accept writes; the transactional outbox claims, publishes and marks rows;
messages cross a real Service Bus topic and are selected by the eventType
filter rules; three consumer hosts receive, dedupe and handle them; and an
edition is assembled by a module that never calls another module
synchronously. Hops 3 and 5 are only reachable through the message path --
the script waits for them rather than asserting on a return value -- so a
broken relay, a missing subscription or a wrong filter shows up here as a
timeout, not as a pass.

Does not prove: concurrency (one collection, one actor, no contention),
ordering (a single event per hop, so nothing arrives out of sequence),
failure handling (nothing was made to fail, so the retry budget,
dead-lettering and the idempotency table were never exercised against a
real duplicate), or the deployed topology (this ran against local SQL, not
the Azure SQL database the Container App uses).

WHAT IT COST TO GET HERE

The first four attempts failed, and none of the causes were visible before
running:

  1. The Service Bus topology did not exist. The provisioning script's dry
     run reported that everything already existed because its probes were
     skipped under -DryRun and a skipped probe returns null, which the
     caller read as "found". Fixed in 10c0507.
  2. az rejected --dead-letter-on-message-expiration; the flag is
     --enable-dead-lettering-on-message-expiration. Fixed in ba7abeb.
  3. EF Core logs every command at Information, and four relays polling on
     a short interval buried the one error that mattered under hundreds of
     heartbeat queries. Fixed in 5d304df.
  4. Adding an item to a saved collection issued an UPDATE for a row that
     had never been inserted, and failed with DbUpdateConcurrencyException.
     Creating a collection worked; adding to it did not. Fixed in 58dd92d --
     see that commit message for why the owner's entity state decided it.

Only the fourth was in the application. The other three were in the tools
meant to verify it, which is its own finding: verification that has never
been run is not verification.
